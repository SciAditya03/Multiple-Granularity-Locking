5. Exam toolkit: Two-Phase Locking (2PL)

Built for questions that ask: (i) the types of 2PL with an example, (ii) show that 2PL gives a conflict-serializable schedule using Li[X] and Ui[X], and (iii) show that locking without 2PL can give a schedule that is not conflict-serializable. This section covers general 2PL material, separate from the multiple-granularity protocol above.

(i) Types of 2PL

Two-phase rule: every transaction has a growing phase (it may only acquire locks) followed by a shrinking phase (it may only release locks). The moment of its last lock acquisition is its lock point. Notation: Li[X] = Ti locks X, Ui[X] = Ti unlocks X.

Basic 2PL

Locks are acquired as needed. After the lock point, locks may be released at any time. Guarantees conflict-serializability. Can suffer deadlock, and cascading rollback because uncommitted data may be exposed after an early unlock.

✓L1[A]→L1[B]→U1[A]→U1[B]

Conservative (static) 2PL

Before executing anything, a transaction locks all items it will use; if it cannot get them all, it waits holding nothing. Deadlock-free, but the read and write sets must be known in advance and concurrency suffers.

✓L1[A]→L1[B]→R1(A)…W1(B)→U1[A]→U1[B]

Strict 2PL

Basic 2PL, plus every exclusive lock is held until the transaction commits or aborts. No other transaction can read or overwrite uncommitted writes, so there are no cascading rollbacks. Deadlock is still possible. (Textbook, 18.1.3)

✓L1[A] X→W1(A)→Commit1→U1[A]

Rigorous 2PL

Even stricter: all locks, shared and exclusive, are held until commit or abort. Transactions are serializable in the order they commit. Deadlock is still possible. (Textbook, 18.1.3)

✓L1[A] S→R1(A)→Commit1→U1[A]

(ii) and (iii) Schedule lab

Type the schedule in time order (top to bottom of your question) as R1(A) W1(A) R2(A)…: R or W, the transaction number, then the item. Reading a column-by-column exam table: go row by row, top to bottom. Lock mode used: S if a transaction only reads an item, X if it ever writes it (this avoids lock upgrades).

How to write the answer

(i) Types of 2PL

Define the two phases and the lock point. Then give one line each for basic, conservative, strict and rigorous 2PL (what is held until when, and one advantage and one drawback), with a short L/U example as in the cards above. Close by noting that basic, strict and rigorous 2PL can deadlock; conservative 2PL cannot.

(ii) 2PL ensures conflict-serializability

Rewrite the schedule with Li[X] before the first use of X and Ui[X] only after the transaction's lock point. If a request conflicts with a lock held by another transaction, the requester waits, so the schedule is reordered. Then draw the precedence graph: an edge Ti → Tj for each conflicting pair (same item, different transactions, at least one write) where Ti comes first. It has no cycle, so a serial order exists (a topological order). Why it always works: order transactions by lock point. For a conflict on X, the earlier transaction must release X before the later one locks it, and that release is after the earlier lock point, so every edge goes from the earlier lock point to the later one. A cycle would need a lock point earlier than itself, which is impossible.

(iii) Locks without 2PL

Show a schedule where each transaction locks and unlocks an item around every operation, so each lock is individually legal, but a transaction unlocks one item before locking another (violating the two-phase rule). Draw the precedence graph of the resulting schedule. Conflicts on one item give Ti → Tj, and conflicts on another item give Tj → Ti, so the graph has a cycle and the schedule is not conflict-serializable.
